# Liferay Form Fragment Development Guide

## Overview

Form fragments (also known as "Page Fragments as Form Fields") are specialized fragments used within a **Form Container**. They bind directly to Liferay Objects or Form Data Providers, allowing for dynamic data entry and validation.

## 1. `fragment.json` Configuration

To be recognized as a form field, the fragment must have a specific type and define which data types it supports.

**CRITICAL**: In Liferay 7.4+, the `type` is usually `input`. Newer versions may use `form`. If you see the error "Only fragment type input can have field types", ensure `type` is set to `input`.

```json
{
  "name": "My Custom Input",
  "type": "input",
  "typeOptions": {
    "fieldTypes": ["text", "number", "date"]
  },
  "icon": "forms",
  "htmlPath": "index.html",
  "cssPath": "index.css",
  "jsPath": "index.js",
  "configurationPath": "configuration.json",
  "thumbnailPath": "thumbnail.png"
}
```

### Supported `fieldTypes`
- `text`, `long-text`, `html`
- `number`, `boolean`, `date`
- `select`, `multiselect`
- `relationship`
- `file`
- `captcha`

## 2. The `input` Global Object

When placed inside a Form Container, Liferay provides a global `input` object in FreeMarker.

| Property | Description |
| :--- | :--- |
| `input.name` | The name attribute for the form field (generated by Liferay). |
| `input.value` | The current value of the field (pre-populated during edits). |
| `input.label` | The field label defined in the Liferay UI. |
| `input.required` | Boolean. True if the field is marked as required in the form settings. |
| `input.errorMessage` | String. Contains the error message if server-side validation fails. |
| `input.readOnly` | Boolean. True if the field should not be editable. |
| `input.attributes` | Map. Contains type-specific metadata (e.g., `min`, `max`, `step`, `dataType`). |

## 3. Implementation Pattern (HTML)

Always wrap your input in a `.form-group` and handle the `input` object properties for a seamless Liferay experience.

```html
<div class="my-custom-input">
    <div class="form-group [#if input.errorMessage?has_content]has-error[/#if] mb-0">
        <label class="[#if !input.showLabel || !input.label?has_content]sr-only[/#if]" for="${fragmentEntryLinkNamespace}-field-id">
            ${htmlUtil.escape(input.label)} 
            [#if input.readOnly]
                (${languageUtil.get(locale, "read-only")})
            [#elseif input.required]
                [@clay["icon"] className="reference-mark" symbol="asterisk" /]
            [/#if]
        </label>

        <input 
            class="form-control" 
            id="${fragmentEntryLinkNamespace}-field-id" 
            name="${input.name}" 
            [#if input.readOnly]readonly[/#if] 
            ${input.required?then('required', '')} 
            type="text" 
            [#if input.value??]value="${input.value}"[/#if] 
        />

        [#if input.errorMessage?has_content]
            <p class="font-weight-semi-bold mt-1 text-danger">
                <svg class="lexicon-icon lexicon-icon-info-circle">
                    <use xlink:href="${siteSpritemap}#info-circle" />
                </svg>
                <span>${input.errorMessage}</span>
            </p>
        [/#if]

        [#if input.showHelpText && input.helpText?has_content]
            <p class="mb-0 mt-1 text-secondary">${htmlUtil.escape(input.helpText)}</p>
        [/#if]
    </div>
</div>
```

## 4. Implementation Pattern (JavaScript)

### Edit Mode Protection
Always disable interactive elements in `layoutMode === 'edit'` to prevent accidental data entry or script execution during page authoring.

```javascript
const inputEl = fragmentElement.querySelector('input');

if (layoutMode === 'edit') {
    if (inputEl) inputEl.setAttribute('disabled', true);
} else {
    // Live mode logic
}
```

### Syncing Complex UI to Hidden Inputs
For fragments with custom UI (like multi-selects, sliders, or flag pickers), use a hidden input with `name="${input.name}"` and sync values via JavaScript.

```javascript
// Example: Syncing a custom UI component to Liferay
customUI.addEventListener('change', (e) => {
    hiddenInput.value = e.target.value;
    // Trigger 'change' on the hidden input so Liferay Form recognizes the update
    hiddenInput.dispatchEvent(new Event('change', { bubbles: true }));
});
```

## 5. Conditional Visibility with Dropzones

You can make parts of a form fragment conditional by using `<lfr-drop-zone>`.

- **Visibility Logic**: Use `has-edit-mode-menu` class in CSS to ensure the dropzone is visible to authors in the editor.
- **Dynamic Display**: Use JavaScript in live mode to toggle `display: block/none` based on field values.

## 6. Best Practices

1.  **Use `input.name`**: Never hardcode the `name` attribute. Liferay uses this to map the field to the correct Object property.
2.  **Escape Labels**: Use `${htmlUtil.escape(input.label)}` for security.
3.  **Handle `required`**: Use `${input.required?then('required', '')}` to enable native browser validation.
4.  **Unique IDs**: Always prefix IDs with `${fragmentEntryLinkNamespace}` to prevent collisions when the same fragment is used multiple times on a page.
5.  **Lexicon Compliance**: Use Clay icons (`asterisk`, `info-circle`) and Lexicon classes (`form-group`, `form-control`, `has-error`) for a native Liferay look and feel.
