# Figma to Liferay DXP Fragment Generator

This skill converts Figma designs (via Figma REST API, full page URLs, local JSON exports, or visual screenshots) into fully compliant Liferay DXP Page Fragments adhering to Clay / Bootstrap 4 standards and Liferay Fragment specifications.

## Workflow Execution Steps

When triggered to create Liferay fragment(s) from Figma:

1. **Fetch & Extract Figma Data**:
   - **Preferred: Hybrid Mode (Figma URL - Design or Prototype)**:
     If a Figma URL (`/design/`, `/proto/` or `/file/`) is provided, run the hybrid fetcher script:
     ```bash
     node .gemini/skills/figma-to-liferay-fragment/scripts/fetch_figma.node.js --url "<FIGMA_URL>"
     ```
     This script automatically extracts BOTH:
     - `figma_tree_<NODE_ID>.json`: Raw text copies, hex colors, font styles, and node hierarchy.
     - `figma_snapshot_<NODE_ID>.png`: High-resolution visual snapshot generated by Figma API.
     
     *Rule*: Combine information from both files! Use `.json` for exact copy/pasting of text and precise CSS values, and `.png` for visual arrangement, overlays, multi-color text spans, and responsive layout decisions.

   - **Fallback 1: Manual Image Screenshot (`--image`)**: Use when no API token is available.
   - **Fallback 2: Local JSON File**: Use when working with exported payloads offline.

2. **Single vs. Multi-Fragment Strategy**:
   - **Single Component / Frame**: Generate a single fragment directory in `./src/liferay-fragments/<fragment-name>/`.
   - **Full Page / Multi-Section**: 
     - Identify top-level sections (e.g., Header, Hero, Features Grid, Call to Action, Footer).
     - Split the layout into modular sections and create a dedicated folder for each section.
     - Generate a root `collection.json` file to package all fragments.

3. **Parse Tree / Visual Structure & Mapping Rules**:
   - Translate layout nodes or visual regions into structured, semantic HTML:
     - Auto-layouts / Grids → Flexbox / Bootstrap Grid (`row`, `col-*`, `d-flex`).
     - Editable Texts → Wrap text nodes in `<lfr-editable id="unique-text-id" type="text">`.
     - Editable Images → Wrap image containers in `<lfr-editable id="unique-image-id" type="image"><img src="..." alt="" /></lfr-editable>`.
     - Action Links / Buttons → Wrap in `<lfr-editable id="unique-link-id" type="link"><a href="#" class="btn btn-primary">...</a></lfr-editable>`.

4. **Generate Fragment Files**:
   For each fragment, generate the required Liferay files:

   - **`index.html`**:
     - HTML5 semantic structure.
     - Liferay tags (`<lfr-editable>`, FreeMarker tags if dynamic rules apply).
     - Clay CSS utility classes (`mb-3`, `text-primary`, `btn`, etc.).

   - **`styles.css`**:
     - Custom CSS extending Clay design system.
     - CSS Variables for dynamic values (colors, spacing).
     - Scoped selectors to prevent global style leakage.

   - **`configuration.json`**:
     - Liferay configuration schema enabling site builders to adjust settings via the UI:
     ```json
     {
       "fieldSets": [
         {
           "label": "General Configuration",
           "fields": [
             {
               "name": "styleVariant",
               "label": "Style Variant",
               "type": "select",
               "dataType": "string",
               "defaultValue": "light",
               "typeOptions": {
                 "validValues": [
                   {"label": "Light", "value": "light"},
                   {"label": "Dark", "value": "dark"}
                 ]
               }
             }
           ]
         }
       ]
     }
     ```

   - **`fragment.json`**:
     ```json
     {
       "cssPath": "styles.css",
       "htmlPath": "index.html",
       "jsPath": "main.js",
       "configurationPath": "configuration.json",
       "name": "Figma Generated Fragment",
       "type": "component"
     }
     ```

5. **Validation**:
   - Verify every `<lfr-editable>` element possesses a unique `id`.
   - Validate `configuration.json` and `fragment.json` against valid JSON syntax.

## Liferay DXP Technical Constraints & Best Practices

To prevent silent failures, import rejections, or responsive rendering bugs, adhere strictly to the following discovered rules:

### 1. Style Book & Theme Token Sourcing (Variables mapping)
- **NEVER hardcode** color hexes, font stacks, or border-radius values in CSS files.
- **ALWAYS ASK the user first** what Liferay theme they are using (e.g., standard **Dialect theme**, standard **Classic theme**, or a custom theme).
- **The Token Definition Dictionary:**
  - This skill contains a local `frontend-token-definition.json` representing all available CSS variables for the default theme (Dialect).
  - The agent MUST parse this local `frontend-token-definition.json` file inside this skill's folder to identify the exact CSS Custom Property mapping name (`cssVariable` or `cssVariableMapping` in mappings) and avoid guessing variable names.
- **For Non-Dialect Themes (e.g., Liferay Classic Theme):**
  - If the user specifies they are using another theme (such as the standard Liferay Classic theme), the agent MUST explicitly advise the user to replace the local `frontend-token-definition.json` file in this skill's folder with the one belonging to their target theme to ensure token-compliance.
  - *Instruction to User:* Explain to the user that they can find their theme's token definition JSON file inside the theme's deployment archive (for instance, inside the `classic-theme.war` or theme directory located within their Liferay installation directory).
- If the **Dialect theme** is used, reference its official CSS variables directly from the mapped definitions:
  - `var(--body-bg)` (instead of `#E3DCCA` or other background colors)
  - `var(--color-brand-primary)` or `var(--color-action-primary-default)` (instead of brand orange)
  - `var(--color-action-neutral-default)` (instead of white `#FFFFFF` for neutral containers)
  - `var(--border-radius-xs)` (instead of hardcoded rounded corners like `4px` or `0`)
  - `var(--color-action-primary-hover)`, `var(--color-action-primary-inverted)`, `var(--color-action-primary-inverted-hover)` (for state-specific buttons)

### 2. The CSS "Gap Trap" on Bootstrap Rows
- **NEVER use CSS `gap` properties** (e.g., `gap: 1.5rem`) on a standard Bootstrap `.row` container that houses percentage-based columns (such as `.col-md-4` or `.col-lg-4` which are mathematically exactly `33.3333%`).
- *The Trap:* Adding a gap breaks the `100%` width flex calculation (it becomes `100% + gaps`), forcing the last column (e.g., the third feature card) to wrap inappropriately onto a second row.
- *The Solution:* Let Bootstrap's native grid padding handle desktop margins. For vertical mobile spacing when stacked, append responsive margin classes like `mb-4 mb-md-0` directly to the column wrappers in HTML.

### 3. Checkbox DataType Schema Restriction
- **NEVER include `"dataType": "boolean"`** for fields of `"type": "checkbox"` in any Liferay `configuration.json` schema.
- *The Trap:* Liferay DXP's configuration engine limits `dataType` to an enum that does not include `boolean`. Including `"dataType": "boolean"` is a validation error that will cause Liferay DXP to silently fail or outright reject the entire fragment collection upon import!
- *The Solution:* Omit `dataType` entirely for checkbox properties; they only require `type`, `name`, `label`, and `defaultValue`.

### 4. Figma Layout Fidelity vs. Subjective Embellishments
- **Fidelity First:** Replicate Figma layouts exactly as designed (columns, rows, spacing, images) without introducing personal or subjective "creative additions" (e.g., adding text overlays on images in a gallery, or transforming plain fields) unless explicitly requested.
- **Unique Keys & Names:** When producing updated iterations of fragments (like `v2`, `v3`, `v6`), ensure that the fragment directory names (which serve as globally unique fragment keys) are uniquely suffixed (such as `-v6`) and the display names in `fragment.json` are distinguished (such as `V6`) to prevent portal collisions and import rejections.
